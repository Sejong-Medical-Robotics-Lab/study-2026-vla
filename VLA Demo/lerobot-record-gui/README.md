# LeRobot Record GUI

Piper 텔레오퍼레이션으로 데이터를 수집할 때 쓰는 제어판.

긴 `lerobot-record` 명령어를 버튼으로 바꾸고, **지금 녹화 중인지 리셋 중인지를
방 건너편에서도 보이는 크기로** 띄우고, 텔레옵이 실제로 동작하고 있는지를
에피소드가 끝나기 전에 알려줍니다.

같은 폴더의 [lerobot-episode-inspector](../lerobot-episode-inspector/)와 한 쌍입니다.
이쪽이 수집, 저쪽이 검수.

---

## 왜 필요한가

로봇 팔을 두 손으로 잡고 텔레옵하는 중에 스크롤되는 터미널을 읽는 건 불가능합니다.
그래서 이런 일이 생깁니다.

- 리셋 시간이 시작된 걸 놓쳐서 물체를 제자리에 못 돌려놓은 채 다음 에피소드가 시작됨
- **텔레옵이 안 붙은 채로 녹화가 도는 걸 30 에피소드 뒤에야 발견함.**
  실제로 inspector 검증에서 ep1·ep2가 이 이유로 fail이 났습니다
- 카메라 인덱스(`index_or_path: 10`, `4`)가 재부팅마다 바뀌어 엉뚱한 카메라로 녹화됨
- `--dataset.root`를 재사용해서 지난 수집분 위에 덮어씀

앞의 둘은 상태 보드와 실시간 지표가, 뒤의 둘은 준비 확인이 잡습니다.

## 실행

**로봇 PC에서** (lerobot이 설치된 venv 안에서):

```bash
source venv/bin/activate
pip install fastapi uvicorn
python server.py --host 0.0.0.0 --port 8010
```

**브라우저에서:** `http://<로봇-PC-IP>:8010`

venv 안에서 띄워야 합니다. 워커가 `lerobot`을 import 해야 하고, 준비 확인의
첫 항목이 그걸 검사합니다.

### 로봇 없이 먼저 만져보기

```bash
uv run server.py --demo --demo-speed 4
```

`fake_worker.py`가 하드웨어 없이 똑같은 프로토콜로 가짜 수집을 돌립니다.
3 에피소드마다 한 번은 **일부러 죽은 녹화**(팔 정지 + 카메라 정지)를 내보내므로
경고 화면이 실제로 뜨는지 확인할 수 있습니다.
`--demo-speed`는 시뮬레이션만 빨리 감습니다 (저장 구간은 그대로).

### 옵션

| 옵션 | 설명 |
|---|---|
| `--host` | 다른 머신에서 접속하려면 `0.0.0.0` (기본 `127.0.0.1`) |
| `--port` | 기본 `8010` (inspector가 8000을 씀) |
| `--python` | 워커를 실행할 인터프리터. 기본은 서버와 같은 것 |
| `--dataset-dir` | 폼의 기본 저장 경로 (기본 `~/lerobot_datasets`) |
| `--set-roles` | `set_roles.py` 경로 |
| `--demo` / `--demo-speed` | 하드웨어 없이 시뮬레이션 |

## 화면

### 상태 보드

| 상태 | 색 | 뜻 |
|---|---|---|
| ● 녹화 중 | 초록 | 지금 데이터가 기록되고 있습니다 |
| ■ 리셋 | 주황 | 물체를 제자리로 되돌리세요 |
| 저장 중 | 파랑 | 영상 인코딩 중 — 로봇을 건드리지 마세요 |
| 강제 종료됨 / 오류 | 빨강 | 로그 확인 |

남은 시간이 큰 숫자로 뜨고, **단계가 바뀌는 순간 브라우저에서 비프음**이 납니다.
소리가 노트북에서 나므로 로봇 PC에 스피커가 없어도 됩니다.
헤더의 `전체화면`을 누르면 보드와 경고만 남기고 나머지가 숨습니다.

남은 시간은 서버 시계가 아니라 **워커가 센 프레임 수 ÷ fps**로 계산합니다.
네트워크가 잠깐 끊겨도 진행바가 어긋나지 않습니다.

### 버튼

| 버튼 | 단축키 | 동작 |
|---|---|---|
| 시작 | | 준비 확인 후 워커 실행 |
| 이번 에피소드 끝 | `→` | 지금 에피소드를 여기서 마감하고 저장 |
| 다시 찍기 | `←` | 지금 에피소드를 버리고 다시 |
| 정지 (저장) | `Esc` | **지금까지 찍은 걸 저장하고** 종료 |
| 강제 종료 | | SIGKILL. 저장 중이던 에피소드가 깨질 수 있음 |

단축키는 LeRobot 원래 키 매핑과 같습니다. 익숙한 사람은 키보드를 그대로 쓰면 됩니다.

**`정지`와 `강제 종료`는 다릅니다.** 정지는 데이터셋을 정상적으로 마감하고,
강제 종료는 인코딩 중이던 파일을 남긴 채 죽습니다. 강제 종료 후에는 반드시
inspector로 마지막 에피소드를 확인하세요.

### 실시간 지표

카메라 영상은 띄우지 않습니다. 30Hz 제어 루프에 부하를 주지 않기 위해서이기도 하고,
데이터를 실제로 망치는 것들이 영상으로는 오히려 안 보이기 때문이기도 합니다.

| 지표 | 잡아내는 문제 |
|---|---|
| 실제 fps / 밀린 프레임 | 루프가 못 따라가면 프레임이 드롭되고 영상-상태 싱크가 깨짐 |
| **움직인 조인트** | 전 조인트 가동범위 1.0 미만 → **`팔이 움직이지 않습니다`** (죽은 녹화) |
| 리더-팔로워 추종 오차 | 명령은 가는데 팔로워가 안 따라옴 |
| 그리퍼 개폐 횟수 | 0회면 대개 실패한 시도 |
| 카메라 변화량 | 직전 프레임과의 차이가 0에 가까우면 화면 정지 |

임계값은 inspector와 같은 값을 씁니다(`STATIC_JOINT_RANGE = 1.0` 등).
**여기서 통과한 에피소드가 나중에 inspector에서 fail이 나지 않도록** 맞춰둔 것입니다.

경고는 단계 시작 후 잠깐(fps·카메라 1.5초, 움직임·추종 3초) 기다렸다 뜹니다.
저장 구간 직후의 정상적인 공백을 문제로 보고하면, 사람이 경고를 무시하게 됩니다.

### 준비 확인

| 항목 | 내용 |
|---|---|
| LeRobot | 워커 파이썬에서 import 되는지, 버전, record 모듈 경로 |
| CAN can4/can5 | UP/DOWN과 bitrate. **`CAN 초기화` 버튼** 제공 |
| 역할 설정 | `set_roles.py` 실행 버튼 |
| 카메라 | `/dev/video*` 열거 + 폼에 적힌 인덱스가 실제로 있는지 대조 |
| 데이터셋 경로 | 이미 존재하면 **빨강** — resume를 켜거나 다른 이름을 쓰라고 안내 |
| 디스크 | 여유 공간 vs 에피소드 수 × 길이 × 카메라 수 추정치 |

`시작`을 누르면 자동으로 한 번 더 돌고, 빨강이 있으면 확인 창이 뜹니다.

#### CAN 초기화에 필요한 sudo 설정

`ip link`는 root 권한이 필요한데, 웹 페이지에는 비밀번호를 칠 수 없습니다.
`sudo -n`(비대화식)으로 실행하므로 NOPASSWD 규칙이 있어야 합니다.
`sudo visudo -f /etc/sudoers.d/lerobot-can`:

```
sejong ALL=(root) NOPASSWD: /usr/sbin/ip link set can* down, \
                            /usr/sbin/ip link set can* type can bitrate *, \
                            /usr/sbin/ip link set can* up
```

규칙이 없으면 버튼이 실패하면서 붙여넣을 규칙을 화면에 보여줍니다.
설정하지 않아도 나머지는 전부 동작하고, CAN은 기존처럼 터미널에서 올리면 됩니다.

### 프리셋

작업(빨간 그릇, 파란 블록…)별로 폼 전체를 저장해두고 불러옵니다.
`presets/*.json`에 저장되며, 폼 하단에는 **실제로 실행되는 명령어**가 그대로 보입니다.
GUI가 뭘 하는지 감추지 않습니다.

## 어떻게 LeRobot에 끼어드는가

**LeRobot 소스는 한 줄도 고치지 않습니다.** `record()`가 쓰는 이름 세 개를
워커 프로세스 안에서 바꿔치기할 뿐입니다.

```python
mod.init_keyboard_listener = lambda: (NullListener(), events)
mod.log_say                = tee_log_say
mod.make_robot_from_config = wrap(mod.make_robot_from_config)
sys.argv = ["lerobot-record", *flags]
mod.record()
```

| 바꾸는 것 | 얻는 것 |
|---|---|
| `init_keyboard_listener` | `events` dict(`exit_early`/`rerecord_episode`/`stop_recording`)를 GUI가 쥡니다. →/←/Esc가 버튼이 되고, **pynput·sudo·비headless 요구가 사라집니다** |
| `log_say` | 단계 전환 시점을 정확히 압니다. stdout 파싱이 아니라 함수 호출 시점입니다 |
| `make_robot_from_config` | 로봇의 `get_observation`/`send_action`을 감싸 프레임 수·조인트 값·카메라 프레임을 가져옵니다 |

설정은 dataclass로 조립하지 않고 **CLI 플래그를 그대로 넘깁니다.** `record()`가
`@parser.wrap()`으로 감싸여 있어 `sys.argv`를 직접 파싱하므로, `piper_follower`
같은 커스텀 로봇 타입의 등록·해석이 명령줄과 100% 같아집니다.

`lerobot.record`(v0.3.x)와 `lerobot.scripts.lerobot_record`(main) 양쪽을 찾습니다.

### 구조

```
브라우저 ──SSE──> server.py (부모)  ──Popen──> recorder_worker.py (자식)
                     ▲                              │
                     └──── POST /api/worker/tick ────┘   (10Hz, 응답에 명령이 실려옴)
```

**녹화가 별도 프로세스인 이유**: 스레드는 CAN 읽기에서 멈추면 죽일 방법이 없습니다.
`강제 종료` 버튼이 의미를 가지려면 자식 프로세스여야 합니다. 자식이 죽어도 GUI는
살아서 이유를 보여줍니다.

**자식이 부모에게 POST하는 이유**: 자식은 어차피 100ms마다 상태를 보내야 합니다.
그 **응답 바디에 대기 중인 버튼 입력을 실어** 보내면 요청 수가 두 배가 되지 않습니다.

**제어 루프에서는 HTTP를 하지 않습니다.** 훅은 슬롯에 값을 대입만 하고,
별도 데몬 스레드가 그걸 읽어 전송합니다. 30Hz 루프에 지터를 주지 않는 것이
이 설계의 최우선 제약입니다 — 녹화 품질을 떨어뜨리는 GUI는 실패한 GUI입니다.

## 구성

| 파일 | 역할 |
|---|---|
| [server.py](server.py) | FastAPI. 워커 생명주기, 상태 보관, SSE, 프리셋 |
| [recorder_worker.py](recorder_worker.py) | 몽키패치 + `record()` 호출. 단독 실행 가능 |
| [preflight.py](preflight.py) | CAN·카메라·디스크·데이터셋 경로 검사 |
| [fake_worker.py](fake_worker.py) | 하드웨어 없는 시뮬레이터. `Metrics`/`Reporter`를 워커에서 그대로 import |
| [static/index.html](static/index.html) | GUI 전체. 외부 의존성 0 |

프론트엔드는 CDN을 포함해 외부 의존성이 전혀 없습니다. 로봇이 인터넷에 연결돼
있지 않아도 동작해야 하므로, 차트도 라이브러리 없이 캔버스로 직접 그립니다.
inspector와 같은 원칙입니다.

### 단독 실행

GUI 없이 워커만 돌려도 동작합니다. `SIGTERM`은 `정지 (저장)`과 같습니다.

```bash
# 설치 상태와 플래그만 검증하고 로봇은 건드리지 않음
python recorder_worker.py --dry-run -- --robot.type=piper_follower ...

# 터미널에서 준비 확인만
python preflight.py --can can4 can5 --cameras 10 4 --root ~/lerobot_datasets/red_bowl_1
```

## 보안

LAN에 `0.0.0.0`으로 여는 서버이므로 임의 명령 실행 경로가 되면 안 됩니다.

- 폼은 자유 문자열이 아니라 **구조화된 JSON**이고, 서버가 화이트리스트에 있는
  플래그만 명령줄로 조립합니다
- 자식은 **리스트로 spawn**됩니다 (`shell=False`). 셸을 거치지 않습니다
- 값은 `[A-Za-z0-9_.:/\-]` 로 제한됩니다. `can5; rm -rf /` 는 거부됩니다
- `/api/worker/tick`은 **loopback + 실행마다 새로 만드는 토큰**으로만 받습니다

인증은 없습니다. 신뢰할 수 있는 연구실 네트워크 안에서만 쓰세요.

## 검증 결과 (2026-08-21)

**하드웨어 없이 (Windows, `--demo`)** — 4 에피소드 시나리오 완주.

- 단계 전환: `record → reset → saving → record → …→ stopping → done`, exit 0
- `다시 찍기` → 같은 에피소드 번호로 재시작, `rerecords` 1 증가
- `이번 에피소드 끝` → 즉시 리셋 단계로
- `정지` → 정상 마감
- 의도적 죽은 녹화에서 `팔이 움직이지 않습니다`(fail)와 카메라 정지 경고 발생
- `강제 종료` → 서버 생존, `강제 종료됨` 표시, 이후 요청 정상 처리

**헤드리스 Chrome으로 화면 검증** — 23개 항목 통과. 페이지 로드부터 시작·조기
종료·정지까지 실제 DOM을 눌러가며 확인했습니다: 콘솔 에러 0, 폼 자동 채움,
명령어 미리보기 생성, SSE 연결, 보드가 초록으로 바뀌고 `● 녹화 중`·카운트다운·
`에피소드 1 / 30` 표시, 지표 카드와 조인트 행 렌더, 실행 중 버튼 활성화, 종료 후 복귀.

브라우저 검증에서 잡은 것:

- **두 번째 수집부터 로그 창이 비었습니다.** 브라우저는 "몇 번 줄까지 봤는지"를
  커서로 기억하는데 서버가 실행마다 줄 번호를 0으로 되돌리고 있었습니다. 새 로그가
  전부 "이미 본 것"으로 걸러졌습니다 — 문제가 터졌을 때 정확히 봐야 할 창이
  비는 버그라, 줄 번호를 계속 증가시키고 `run_id`로 초기화를 알리도록 고쳤습니다
- 폼을 한 번 수정하면 이후 모든 갱신에서 설정 패널이 강제로 접혔습니다.
  이제 실행 시작/종료 **전환 시점에만** 접고 폅니다
- 경고가 뜨면 버튼이 아래로 밀렸습니다. 팔을 잡은 채 누르는 버튼이라 위치가
  움직이면 안 됩니다 — 버튼을 경고 위로 올렸습니다
- 전체화면이 글자 크기 그대로라 공간만 비었습니다. 타이포를 키웠습니다

**LeRobot 스텁 대상 (`recorder_worker.py` 실제 경로)** — 실제 `record()`와 같은
구조의 스텁 모듈에 몽키패치를 걸어 확인. 단계 감지, 버튼, `listener.stop()`을
호출하는 finally 블록 통과(exit 0), `--dry-run`의 모듈 해석 모두 정상.

**지표 단위 검사** — 15개 항목 전부 통과. 특히:

- 그리퍼를 **위치가 아니라 이름으로** 찾는지. Piper는 관측 dict를 정렬하면
  `gripper.pos`가 **맨 앞**에 옵니다(`g` < `j`). 마지막 열을 그리퍼로 가정하면
  joint 6의 개폐 횟수를 세게 됩니다 — 실제로 그렇게 만들었다가 고쳤습니다
- 단계가 바뀔 때 프레임 시계가 초기화되는지. 초기화하지 않으면 저장 구간의
  공백이 새 단계의 첫 주기로 측정돼 **에피소드마다 가짜 fps 경고**가 뜹니다

**아직 실측하지 않은 것**

- 실제 Piper·CAN·카메라 연결 상태에서의 동작
- **GUI가 붙었을 때 달성 fps가 떨어지지 않는지.** 훅은 슬롯 대입뿐이고 HTTP는
  별도 스레드지만, 같은 설정으로 GUI 있이/없이 돌려 `timestamp` 간격 분포를
  비교해야 확정입니다
- 실제 `lerobot` 패키지(v0.3.x / main) 상대의 몽키패치. 스텁으로만 확인했습니다
